# 方向修正 — 2026-07-31

## 触发

2026-07-31 对抗式审查（`adversarial-review-2026-07-31.md`）发现：

1. 系统愿景（VISION §2.3 七问）与当前生产报告的实际覆盖存在 3 项完全缺失、2 项部分覆盖；
2. shadow 管道（`advisory_synthesizer`）已就绪但未接入主链路；
3. Research 候选（含短中期布局建议）在报告层被隐藏；
4. 上一轮"去掉 outlook 重定位为决策校验器"的建议与用户核心目标（结合新闻/产业/情绪的走势研判 + 短中期操作 + 提前布局）冲突，已推翻。

## 用户核心目标（本次校验后的最终版本）

> 能够结合新闻实事、产业报告内容和市场情绪来分析市场走势，给出短中期操作建议和提前布局建议的交易助手。

**关键约束**：
- 单用户使用；
- 用户自己下单，系统不需要执行链路；
- 走势研判（outlook）是核心价值，不可裁减；
- 用户接受"经验证的 LLM 综合判断"，不接受"规则拼接结论"。

## 新的系统定位

**每日/每窗口给用户一份决策叙事**，包含：

1. **走势研判**：短期（3-7 天）与中期（1-3 月），基于新闻、产业信号、情绪、宏观和技术面，带条件和证伪线；
2. **可执行动作**：短中期操作建议，含幅度、参考金额、执行条件、取消条件；
3. **提前布局候选**：中期机会，含左侧/右侧类型、试仓建议、复核条件；
4. **组合与风险**：当前风险状态、资金结构、执行后影响；
5. **数据边界**：什么数据不可靠、什么情况暂停判断；
6. **下一检查点**：时间/价格/事件/数据条件。

每条建议必须携带来源引用（source_refs）与新鲜度标注。

## Roadmap 收敛：M1 → M2 → M3

### M1 — 报告层重构（预计 1-2 周）

**目标**：让报告匹配 VISION §2.3 的 7 问结构，让已经存在的内部字段流出到用户面前。

**核心动作**：
- 报告结构从 5 段升级为 6 段：**本窗口变化 / 走势研判 / 可执行动作 / 提前布局 / 禁止与延后 / 组合与检查点**；
- Research candidates 从 count 一行升级为独立"提前布局"段，展示 top 2-3 候选的完整叙事（display_label、action_hint、reassess_after、综合得分）；
- Manual review 状态下"可执行动作"与"禁止与延后"去重，动作段明确列出"待用户确认的选择空间"（含参考比例/金额）；
- Data notes 中的资金缺口（如"¥4,790 结算方式待确认"）必须进入报告；
- 现金 6 桶按重要性折叠：`confirmed_settling=0` 时省略，`strategic_exit` 仅当有卖出动作时显示；
- Truth gate 拒绝的动作保留"原始意图"（signal_type、instrument、参考比例）作为审计线索并投影到报告。

**验收**：
- 现实报告样本对照 VISION §2.3 七问，覆盖度从 2/7 → 至少 5/7（走势研判部分留给 M2）；
- 单元测试覆盖新的"提前布局"段和 manual_review 去重逻辑；
- Ruff / pytest / compileall 全绿。

**依赖**：无。可立即开始。

### M2 — Outlook 主线化（预计 3-4 周，本迁移的核心价值）

**目标**：把 shadow 管道 `advisory_synthesizer` 接入生产主链路，用 LLM 综合新闻/产业/情绪/宏观/技术信号，产出可验证的走势研判。

**核心动作**：
- 打开 outlook synthesizer 配置开关，接入 `UnifiedAnalysisSnapshot`；
- 走势研判必须携带 `source_refs`（`AdvisoryValidationReceipt` 已有验证逻辑）；
- 短期研判 3-7 天，中期研判 1-3 月，各带条件和证伪线；
- 保留数据新鲜度门槛（当前生产链路已实现，不可倒退）；
- 生产链路 fallback：Outlook 生成失败或校验不通过时，报告降级为"研判待复核"，绝不推测；
- 提供 shadow 对照工具（`compare_advisory_paths.py` 已存在），主线化前用 5-10 天的历史数据回放校验一致性。

**验收**：
- 报告七问覆盖从 5/7 → 7/7；
- 至少 10 个真实窗口的研判具备 source_refs 且未触发降级；
- Shadow 对比工具显示新老路径关键结论一致（方向、置信度、驱动源）；
- 用户手动确认"研判段有决策价值"。

**依赖**：M1 完成（报告层能承接研判输出）；LLM 提供方稳定（当前已配置多个 provider）。

### M3 — 反馈闭环（预计 2 周）

**目标**：把用户对建议的处理反馈接进系统，为未来的自适应校准奠基。

**核心动作**：
- 报告推送后，提供轻量的用户回应通道（Feishu 卡片按钮或 CLI 命令）：`accepted` / `partial` / `rejected` / `deferred`；
- 用户回应写入 `AdviceRecord`（这是原 TASK-002 的合理落脚点，聚焦"反馈"而非"草稿建议"）；
- 每周自动 review：命中率、拒绝原因归因、报告七问覆盖趋势；
- 反馈只作为未来 outlook 的**输入证据**（`recent_advice` 已在 `AnalysisContext` 中存在），不做自动参数调整。

**验收**：
- 用户能对每条建议标记反馈；
- 每周 review 报告能显示至少 4 类统计（覆盖率、命中率、主要拒绝原因、数据边界暴露次数）。

**依赖**：M2 完成（有真正的建议可反馈）。
