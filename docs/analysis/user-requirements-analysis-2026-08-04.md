## 6. 结论：需求的本质（修正版）

**用户的组合是"双核 + 一轴"结构**：

1. **美元/科技核**（¥25.6 万）：纳指 QDII + IBKR（NVDA/XLE/ITA/NEM/
   SGOV + 70% 待部署美元现金），部署方向是美国市场，由美联储路径、
   AI 产业链、美股估值驱动；
2. **人民币核**（场内 ¥4.7 万 + 待部署现金 ¥37 万）：当前是试验田，
   但现金部署方向是 A 股，由中国政策周期、A 股估值、市场情绪驱动；
3. **黄金轴**（¥26.4 万）：横跨两池的独立敞口，由实际利率、央行
   购金、美元信用叙事驱动；
4. **汇率层**（USD/CNY + QDII 溢价）：连接两核的定价层。

**因此需求不是"以中国资产信息面为核心"，而是"以敞口地图为核心、
双引擎并重"**：信息系统必须同时覆盖美元流动性与科技链（服务现有
最大权益敞口 + IBKR 部署）和中国周期与政策（服务人民币核建仓），
黄金与汇率作为两条横切层。用户需要的不是"更快的交易信号系统"，
而是一个**以估值与周期为锚、以不可逆约束和纪律为骨架、双引擎
并重的"建仓与配置决策支持系统"**。

**AI/半导体产业链是唯一同时贯穿两核的主题**（NVDA + 纳指 QDII +
易方达信息产业 ↔ 半导体 512480 + 未来 A 股科技部署）——单一信息
投入可同时服务两侧决策，是杠杆率最高的信息主题。

三个层次的优先级（修正版）：

1. **第一优先：D1/D2 信息面，双引擎同时建**——
   - 美元侧：纳指/美股估值锚（CAPE/分位）、AI/半导体产业新闻
     （中英双语）、QDII 溢价率；英文宏观新闻已有，缺的是估值锚；
   - 人民币侧：中国宏观（PMI/社融/LPR）、A 股估值分位、中文财经源
     （华尔街见闻/财联社/东财）、A 股情绪指标（成交额/北向）。
   这是双侧 65 万现金部署决策与 13 万不可逆 QDII 决策的共同前提。
   没有估值锚，任何一侧的"走势研判"都只是技术面外推。
2. **第二优先：M4 约束模型**（不可逆/分池/硬上限）——用户决策结构
   的骨架；分池语义正是"双核"结构的系统表达。
3. **第三优先：D6 纪律闭环真正运转**——M3 反馈、forecast 结算、
   推送自动化。机制都在，差的是"用起来"。

中文新闻源（此前对话焦点）是人民币侧信息面的子集，单独做价值
有限；应与美元侧信息面一起作为"双引擎信息面"整体建设。

1. **M4 落地**（最高优先）：把约束语义（no_buyback/pools/hard_caps）
   以确认式写入的金融记忆/config 表达——M4 任务文件的 schema 设计
   经验证覆盖你的全部硬约束（限购→no_buyback、封闭池→isolated
   pool、12%→hard_cap、换汇难→pool isolated 语义包含）。开放期日历
   （liquidity.lockup_until 填充）需一并补数据。
2. **信息面派生化**：instrument 元数据（exposure_tags/product_type/
   market）→ 信息主题与查询面的映射放配置，代码零持仓知识；清理
   `category_to_positions` 腐烂映射，改为从资产文件反推。
3. **纪律原则固化**：与单个持仓绑定的知识只允许有一个权威来源——
   资产文件本身；配置只放类型级规则；代码零持仓知识。任何新持仓
   经 A1 确认式录入后，自动获得：结算规则、约束检查、信息覆盖、
   报告呈现，无需改代码。

## 9. 分发行与用户中立化（2026-08-04 第三轮，用户明示）

> 用户明示：系统后续可能分发给其他用户使用。约束内容（以及一切用户
> 特异信息）不能写死——"非硬编码架构"的深层目的即**多用户分发**。

### 9.1 架构原则：系统 vs 实例三层分离

| 层 | 内容 | 规则 |
|---|---|---|
| 代码 | 引擎、规则、渲染 | 零用户知识：无账户 ID、无平台名、无标的代码、无约束值 |
| 分发配置 | engine.yaml、schema、类型级规则 | 只有 schema + 中性默认值 + 类型级规则；与实例数据合并加载，缺数据 fail-closed |
| 实例数据（每用户私有，永不入分发包） | 持仓、账户、平台、约束、画像、自选股、信息源偏好、池划分 | 全部在 `.local/` + `.secret/`，确认式写入 |

分发体验目标：新用户得到"空白但完整"的引擎，经 A1 确认式录入自己的
持仓与约束后，系统按同一套类型级规则为其工作。

### 9.2 现状审计（2026-08-04，实证）

代码/分发配置中的用户特异信息共 **168 处命中**（个人账户 ID、平台名、
持仓 ID 出现在 `.py` 与默认配置中）：

- `presentation.py`：操作渠道写死"支付宝/建行 APP/中银人寿/IBKR"
- `quant_action.py` / `config_loader.py` / `intelligence_analyzer.py`：
  写死用户持仓 ID（alipay_gf_nasdaq、ccb_gold 等）
- `stocks/config/portfolio_constraints.json`：用户真实四桶比例值在
  **分发仓库配置目录**（加载只查 config_dir，无 `.local/` 优先路径，
  与 investor_profile.json 的处理方式不一致）
- `category_to_positions` 腐烂实证（§8.3）：9 类中 6 类含幽灵持仓——
  正是"用户知识写死在系统里"的直接危害
- 2026-08-03 修复中加入的账户 ID 兜底表（cn_broker/bochk_life）
  属务实过渡，元数据透传路径稳定后应退役

**结论：今天直接分发本 repo，其他用户会带着本用户的平台、约束与
持仓映射运行并得到错误建议。**

### 9.3 设计规则（分发目标下的硬规则）

1. **派生优于映射**：平台显示名从账户 display_name 派生、机构类型从
   账户元数据派生、信息映射从 exposure_tags 派生；凡能派生，禁止
   写第二份。
2. **约束即金融记忆**：约束 schema（含 M4 扩展）在 repo 只放结构与
   example；约束值加载路径改 `.local/` 优先 + fail-closed 校验。
3. **用户中立化工作流**（路线图新增，可并入 M4 + 独立清理任务）：
   迁移约束加载路径、清除代码中 168 处用户知识、分发配置 example 化、
   账户 ID 兜底表退役。
4. 产品不变式延伸：**实例数据永不随分发包流出**；repo 中的 example
   数据不得可被误认为真实用户数据（命名/注释明示）。
